# OpenOcti 1.4.0

This release adds an approval gate for agent actions. Anything an agent does that sends, spends, or grants access is refused unless a human approves that exact call.

- Agent tool calls run against a declared risk policy. Sending email or SMS, placing calls, sending payment links, recording payments, issuing credits, granting portal or voice access, deleting records, and paid generation all require approval. Reading, searching, and ordinary CRM record-keeping run unattended as before.
- Approvals are bound to one specific call — the tool, its arguments, and the tenant. They are single-use and expire. An agent cannot approve itself, and an approval claim placed in a tool's own arguments grants nothing.
- Approving is done from the Command Center by a signed-in administrator, through the approvals panel or Settings. The approvals API accepts no machine credential.
- For demonstrations and supervised work, an administrator can open a time-boxed window during which qualifying actions run without a prompt for each one. Windows are capped in code, show a countdown while open, and can be closed at any time.
- A refused call now returns a pending approval rather than a bare rejection, and the agent is instructed to say it is waiting rather than report success. This replaces a failure mode where a blocked action was indistinguishable from a completed one.
- Every attempt, grant, and use is written to an audit log, recording which approval or window allowed an action and who decided it.
- Unknown tools are treated as requiring approval. Every tool must be explicitly declared safe to run unattended; anything undeclared is refused. A test fails the build if a tool is left unclassified.
- Settings gains an Agent Approvals screen: notification channels, approval expiry, the maximum window an administrator may open, recent approval activity, and a searchable table of every tool that requires approval.
- Approval notices can be delivered by push notification, by email, or both.
- Time entries can record a project. When a client has more than one project, the timer offers a project choice; clients with one project or none are unchanged.
- A browser extension for harvesting business leads from map listings is included under `tools/`, with its own installation notes. It is configured against your own installation and holds no preset server.

## Fixes

- Agent-initiated timer commands failed authentication and silently did nothing. The timer now accepts the same machine credential as other agent endpoints.
- Tool arguments sent at the top level of a request, rather than nested, were discarded and reported as missing. Both shapes are now accepted.

## Installing and upgrading

Follow the [getting-started guide](../guides/getting-started.md). Back up your existing data and configuration before upgrading.

No configuration is required to adopt the approval gate. With no settings file present, the defaults reproduce this release's documented behaviour: push notifications on, email off, approvals expiring after fifteen minutes, and a maximum window of two hours.

To use the lead extension, set `FCC_MAPS_INTAKE_TOKEN` in your environment and enter the same value in the extension, or stay signed in to your installation in the same browser profile.

This package uses only its installation's configuration, accounts, and credentials. It does not include private business records or access to Farrington services.

Client portal provisioning and the new-business outreach automation are commercial capabilities and are not included. Their agent tools are present and gated like any other, but report that the capability is unavailable rather than acting.

## Verification scope

The approval sequence was exercised end to end against a running installation: a refused action, an administrator approval, the same call then succeeding, the approval refusing reuse, a time-boxed window carrying several actions, closing that window, and the gate returning. A machine credential was confirmed to be rejected by the approvals API. The settings screen and push notification delivery were verified in a browser. The full automated suite passes apart from failures that predate this work.

A fresh Docker Compose installation was not built for this release, and email delivery of approval notices was exercised only through the settings test action, not through a live approval. The lead extension's code was reviewed and its defaults verified, but it was not installed in a browser against a clean installation. Complete the guide's installation checks in your own environment before relying on any of this in production.
